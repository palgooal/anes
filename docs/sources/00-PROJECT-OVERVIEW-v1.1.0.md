## 1. تعريف المشروع — Project Definition

نظام أنيس (ANIS) منصة رقمية للرعاية والمساندة، توفر موقعًا إلكترونيًا للتعريف بخدمات المؤسسة وحجز الاستشارات، إلى جانب لوحة إدارة مخصصة لإعدادات الموقع والهوية البصرية والعمليات التشغيلية.

تُطوَّر النسخة الأولى لمؤسسة واحدة، ولا تشمل نظامًا ديناميكيًا لإدارة أقسام الصفحة الرئيسية أو منصة SaaS أو Multi-Tenant.

يجمع النظام بين إعدادات الموقع الأساسية وإدارة العمليات المرتبطة بالاستشارات والحجوزات ضمن لوحة تحكم موحدة.

## 2. أهداف المشروع — Project Objectives

1. إطلاق موقع إلكتروني يعكس هوية أنيس ويعرّف بخدماته.
2. تمكين المستفيدين من حجز الاستشارات الحضورية وعن بُعد.
3. توفير نظام مركزي لإدارة أنواع الاستشارات ومقدمي الخدمة والمواقع والجداول.
4. تنظيم المواعيد والسعة ومنع الحجوزات المتعارضة.
5. تمكين الإدارة من متابعة الحجوزات وإسنادها وإعادة جدولتها وإلغائها وإغلاقها.
6. توفير لوحة إدارة لإعدادات الموقع الأساسية والهوية البصرية، تشمل اسم الموقع ووصفه والشعار والألوان ومعلومات التواصل، مع تأجيل إدارة أقسام الصفحة الرئيسية إلى مراحل تطوير لاحقة.
7. توفير صلاحيات إدارية منفصلة حسب المسؤوليات.
8. توفير إمكانية مزامنة بيانات الحجوزات إلى Google Sheets بصورة اختيارية وأحادية الاتجاه.
9. تأسيس بنية قابلة للصيانة والتوسع مستقبلًا دون تنفيذ وظائف SaaS في الإصدار الأول.

## 3. طبيعة النظام — System Classification

**Single-Organization Website Administration with Consultation Booking Management**

المكونات الوظيفية الرئيسية:

- **Public Website:** الموقع العام وصفحات المحتوى والحجز.
- **Site Settings & Branding:** إدارة الهوية البصرية وإعدادات الموقع ومعلومات التواصل الأساسية.
- **Consultation Operations:** إدارة الاستشارات والمواعيد والحجوزات ومقدمي الخدمة.

تستخدم هذه المكونات بيانات النظام المركزية، مع فصل المسؤوليات والصلاحيات بينها.

## 4. المستخدمون — System Actors

### 4.1 الزائر / طالب الخدمة

يستطيع استعراض محتوى الموقع واختيار الاستشارة والموعد وتقديم بيانات الحجز وإتمام آلية التحقق التي ستُعتمد لاحقًا. لا يحتاج إلى حساب مستخدم مستقل في النسخة الأولى.

### 4.2 المستفيد

الشخص الذي ستُقدم له الاستشارة، وقد يكون هو طالب الخدمة نفسه أو أحد ذويه.

### 4.3 Super Admin

المدير الرئيسي المسؤول عن إعدادات النظام والموقع والهوية البصرية والمستخدمين وإدارة عمليات الاستشارات.

### 4.4 Consultation Admin

مسؤول تشغيل الاستشارات والحجوزات، بما يشمل الحجز اليدوي والإسناد والمتابعة والإلغاء وإعادة الجدولة وإغلاق الحجوزات.

### 4.5 Service Provider

الشخص الذي يقدم الاستشارة، وتُدار بياناته وجداوله وإسناداته بواسطة الإدارة. لا يمتلك حساب دخول مستقلًا في MVP.

## 5. حدود النسخة الأولى — MVP Boundaries

- صفحة رئيسية وفق التصميم المعتمد من العميل، بأقسام ثابتة البنية والمحتوى.
- إدارة اسم الموقع ووصفه التعريفي الأساسي.
- إدارة الشعار وFavicon والألوان العامة للموقع.
- إدارة رقم الهاتف والبريد الإلكتروني والعنوان ورابط WhatsApp وروابط التواصل الاجتماعي.
- Header وFooter وفق التصميم المعتمد، مع عرض المعلومات الأساسية القابلة للتعديل من إعدادات الموقع في المواضع المحددة.
- إدارة المستخدمين الإداريين والصلاحيات.
- إدارة أنواع الاستشارات.
- إدارة مقدمي الخدمة.
- إدارة المواقع الحضورية.
- إدارة الجداول والاستثناءات.
- Availability & Capacity Engine.
- حجز الاستشارات الحضورية وعن بُعد.
- **التحقق من بيانات التواصل قبل تأكيد الحجز العام — قيد الدراسة.** تُحدد آلية التحقق المناسبة لاحقًا بعد دراسة سهولة الاستخدام والأمان والتكلفة ومتطلبات التشغيل.
- الحجز اليدوي بواسطة الإدارة.
- الإسناد اليدوي وإعادة الإسناد.
- إعادة الجدولة والإلغاء والإكمال وNo-show.
- Dashboard تشغيلية.
- Audit Log.
- Google Sheets Sync اختياري وأحادي الاتجاه.

تُفصّل هذه الوظائف في وثيقة SRS مستقلة.

## 6. المبادئ التشغيلية — Core Principles

### 6.1 مصدر البيانات

قاعدة بيانات أنيس هي المصدر الرسمي والوحيد للحجوزات والبيانات التشغيلية. لا تُستخدم Google Sheets كمصدر بديل للحجوزات أو لحساب السعة والتوفر.

### 6.2 سلامة الحجوزات

لا يجوز تأكيد حجز يتجاوز السعة المتاحة أو يتعارض مع قواعد المواعيد.

### 6.3 الإسناد

يختار طالب الخدمة نوع الاستشارة والموعد، ولا يختار مقدم الخدمة. تتولى الإدارة إسناد مقدم الخدمة المؤهل والمتاح.

### 6.4 التحقق — Under Study

يحتاج الحجز القادم من الموقع إلى آلية تحقق مناسبة قبل تأكيده، وتُحدد هذه الآلية بعد دراسة الخيارات المتاحة واعتمادها.

الحجز اليدوي بواسطة الإدارة لا يحتاج إلى تحقق OTP من المستفيد، مع الالتزام بقواعد التوفر والسعة.

### 6.5 استقلالية التكاملات

لا تعتمد سلامة البيانات أو نجاح الحجز على توفر Google Sheets.

تُصمم آلية التحقق بحيث لا ترتبط بمنصة إرسال محددة قبل اعتماد وسيلة التحقق النهائية.

## 7. حدود النظام — Out of Scope

- SaaS / Multi-Tenancy.
- إدارة اشتراكات المؤسسات.
- بوابات الدفع الإلكتروني.
- الاستشارات المدفوعة.
- حسابات مستقلة للمستفيدين.
- بوابة مستقلة لمقدمي الخدمة.
- الإسناد التلقائي.
- تكامل WhatsApp الآلي لأغراض التواصل التشغيلي (أما وسيلة التحقق فلم تُحسم بعد).
- إنشاء روابط الاجتماعات تلقائيًا.
- إلغاء أو إعادة جدولة الحجوزات ذاتيًا.
- SEO Management Module.
- Application Backup Management Module.
- المصادقة الثنائية للإدارة 2FA.
- Full Page Builder.
- تعديل محتوى أقسام الصفحة الرئيسية من لوحة الإدارة.
- إضافة أقسام الصفحة الرئيسية أو حذفها أو إخفاؤها أو إعادة ترتيبها.
- مكتبة قوالب أقسام قابلة لإعادة الاستخدام.
- إدارة عناصر قوائم Header وFooter وترتيبها أو تغيير تصميمهما من لوحة الإدارة.

تُسجل المتطلبات المستقبلية دون تنفيذها ضمن MVP.

## 8. توجهات التصميم والتقنية

- واجهة عربية RTL-first.
- تصميم Responsive لجميع الشاشات.
- Admin Dashboard مخصصة دون استخدام لوحات إدارة جاهزة.
- تصميم Prototype باستخدام Tailwind CSS بعد اعتماد متطلبات UI/UX.
- Laravel وMySQL خيارات مبدئية لمرحلة التنفيذ، تخضع للمراجعة المعمارية.
- لا يبدأ تنفيذ Backend أو قاعدة البيانات قبل اكتمال التوثيق والتصميم وموافقة العميل.

## 9. منهجية التنفيذ والاعتماد
